# รายงานการใช้ AI

รายงานนี้สรุปว่าใช้ AI ทำอะไร ในส่วนไหนของโปรเจ็ค และตรวจสอบผลอย่างไร (งาน 11.5)
หัวข้อ 1–4 และ 6 เป็นงานของ Phakkathima ส่วนหัวข้อ 5 เป็นงานระบบของ Pattarakorn (Database, Auth, Server Action)
ปรับปรุงหลังงานหลักและงาน Bonus (9.4 Export CSV, 9.5 Dark mode) เสร็จ ตัวเลขและเลข PR อ้างอิงจาก GitHub ณ ตอนนั้น

## 1. เครื่องมือและหลักการใช้

| รายการ | รายละเอียด |
|---|---|
| เครื่องมือ | Claude Code (AI coding assistant ที่รันในเครื่อง ผ่านส่วนขยายใน VS Code) |
| ผู้ใช้ | Phakkathima (ส่วน CI, test, components, เอกสาร) |
| วิธีทำงาน | สั่งงานเป็นข้อๆ ให้ AI เขียนหรือแก้ไฟล์ในเครื่อง AI รัน lint, tsc, build และ test แล้ว commit ในเครื่อง พร้อมสรุปผลและสิ่งที่ตรวจไม่ได้ ให้ผู้ใช้ตรวจ |
| ผู้ตัดสินใจ | คน ไม่ใช่ AI: push, เปิด Pull Request และ merge ทำเมื่อผู้ใช้สั่งเท่านั้น (ทุกครั้ง ไม่ถือว่าคำสั่งครั้งก่อนครอบคลุมครั้งถัดไป) ส่วนโพสต์คอมเมนต์และเลือก Reviewer ผู้ใช้อนุญาตไว้ล่วงหน้า และอีกคนในทีมเป็นคนรีวิวและ merge งานของเรา |

หลักการที่ตั้งไว้ใน [AGENTS.md](../AGENTS.md) ซึ่ง AI อ่านทุกครั้งที่เริ่มทำงาน

- ทำงานตามขอบเขตของเจ้าของงาน: branch `design/*` แก้ได้เฉพาะ markup, styling และ `components/`
  ห้ามแตะ Server Action, data fetching, validation, migration, RLS และ `lib/supabase/`
  ถ้าต้องแก้ ให้หยุดและถามเจ้าของงาน
- commit ย่อยทีละเรื่อง ข้อความเป็นภาษาอังกฤษ ไม่มีการระบุเครื่องมือ AI ใน commit, PR และคอมเมนต์ในโค้ด
- ก่อน commit ต้องรัน `npm run lint`, `npx tsc --noEmit` และ `npm run build` ให้ผ่าน
- ห้าม commit `.env.local` หรือ key จริง และห้ามให้ Service Role Key ปรากฏในโค้ดฝั่ง Client

เรื่องข้อมูลลับ: การตั้งค่าใน `.env.local` ทำเองโดยผู้ใช้ และในงานที่ผ่านมา AI ไม่ได้เปิดอ่านหรือพิมพ์ค่าในไฟล์นั้น
(มีเพียงย้ายไฟล์ชั่วคราวเพื่อทดสอบว่า build ผ่านด้วยค่า dummy แล้วคืนที่เดิม และใช้ `grep -c` นับว่าบรรทัด `SUPABASE_SECRET_KEY` ว่างอยู่ไหม ได้เป็นตัวเลข 0 หรือ 1 ไม่เห็นค่า) และตามแผนงานข้อ 0.4 ผู้ใช้ไม่ต้องใช้และไม่ได้รับ Service Role Key

## 3. ตรวจสอบผลอย่างไร

ไม่เชื่อผลจาก AI โดยอัตโนมัติ ทุกงานผ่านขั้นตอนต่อไปนี้

| วิธีตรวจ | ทำอย่างไร |
|---|---|
| ตรวจอัตโนมัติในเครื่อง | รัน `npm run lint`, `npx tsc --noEmit`, `npm run build` และ `npm test` ก่อน commit ทุกครั้ง |
| CI | GitHub Actions รัน install, lint, build และ test บนทุก push และ Pull Request ต้องขึ้นเขียวก่อน merge |
| ทดสอบว่า test จับบั๊กได้จริง | หลังเพิ่ม regression test ของ ConfirmDialog ได้ลองรันกับโค้ดเก่า test ต้องล้ม แล้วรันกับโค้ดที่แก้ต้องผ่าน |
| ทดสอบ CI แบบไม่พึ่งค่าจริง | ย้าย `.env.local` ออกแล้ว build ด้วยค่า dummy อย่างเดียว เพื่อยืนยันว่า workflow ไม่ต้องใช้ key จริง |
| เทียบกับเอกสาร | ตรวจ test checklist และ README เทียบกับ `docs/REQUIREMENTS.md` และแผนงาน |
| ตรวจข้อมูลลับ | ค้นหา pattern ของ key, JWT และอีเมลในไฟล์ที่เขียนใหม่ก่อน commit |
| ตรวจโดยเพื่อนร่วมทีม | ทุกงานเปิด Pull Request ให้อีกคนรีวิวและเป็นคน merge |
| ตรวจขอบเขต | ดู `git diff` ว่าแก้เฉพาะไฟล์ที่อยู่ในขอบเขตของ branch นั้น และดูแบบสามจุด (`main...branch`) เพื่อให้เห็นเฉพาะงานของ branch ไม่ปนงานที่ merge เข้ามาแล้ว |
| ถ่ายภาพหน้าจริงหลายขนาดจอและทั้งสองโหมด | ใช้ Chrome แบบไม่มีหน้าต่างถ่ายที่ 360, 768, 1024 และ 1280 px ผ่านหน้าพรีวิวชั่วคราวที่ไม่ commit (เพิ่มเส้นทางเข้า `PUBLIC_PATHS` ในเครื่อง แล้วถอนคืนและตรวจ `git status` ก่อน commit ทุกครั้ง) พบปัญหาที่ test มองไม่เห็น เช่น ตารางที่ซ่อนสถานะบนมือถือ, Navbar ที่ตกบรรทัดที่ 768 px และป้ายที่ถูกตัดขอบ |
| ทำให้โค้ดเสียแล้ว test ต้องล้ม | หลังเจอ test ที่ผ่านเสมอโดยไม่ได้ตรวจอะไรจริง (#10) test ใหม่ของงานตกแต่งและงาน Bonus ถูกลองทำให้โค้ดเสียก่อน เช่น ถอด BOM, ถอดตัวกัน CSV injection, ข้าม `requireUser`, ถอดสคริปต์ออกจาก `<head>` ต้องมี test ล้ม และต้องเช็กว่าการแก้โค้ดติดจริง (ไม่ใช่คำสั่งแก้ที่ไม่ได้เปลี่ยนไฟล์) |
| ตรวจในเบราว์เซอร์จริงด้วยโปรแกรม | Dark mode 21 ข้อ (ไม่มีหน้าขาวแวบโดยดูว่า class ถูกตั้งก่อนที่ `<body>` ปรากฏ, จำค่าหลัง refresh, ตามเครื่องในโหมด System, `localStorage` ถูกบล็อก, คีย์บอร์ด) และเปิดสองแท็บอีก 9 ข้อ |
| Postgres จำลองที่รัน migration จริง | รัน migration ทั้งหมดและ seed บน Postgres ในเครื่อง แล้วทดสอบสิทธิ์ของแต่ละ role, trigger, ตัวเลข Dashboard และการดึงข้อมูลทีละหน้าที่จำลองเพดาน Max rows ข้อจำกัด: ไม่ใช่ Supabase จริง จึงไม่มีส่วนเสริมและ role ของ Supabase |
| เรนเดอร์เอกสารด้วย GitHub จริง | ส่ง README และรายงานนี้ให้ markdown API ของ GitHub แล้วนับตารางที่เรนเดอร์ และดึงรหัส anchor ของหัวข้อภาษาไทยจากผลจริงมาทำสารบัญ แทนการเดา |
| อ่านเอกสารของ Next.js 16 ก่อนเขียน | ตามที่ AGENTS.md กำชับ: คู่มือป้องกันหน้ากะพริบก่อน hydrate (Dark mode), Route Handler (Export CSV), `useFormStatus` (ปุ่มส่งฟอร์ม) |
| ตรวจว่า PR ไม่ชนกันและทดสอบผลรวม | `git merge-tree` กับ PR ที่เปิดอยู่ทุกอัน และเมื่อมี PR สองอันที่เกี่ยวกัน (#43, #44) รวมเข้า `main` ในเครื่องแล้วรัน test ทั้งชุด (262 ตัว) ก่อน merge |
| ยืนยันว่า merge ตัวที่ตรวจจริง | ก่อน merge ทุกครั้งเช็กว่าหัวของ PR เป็น commit เดียวกับที่ตรวจหรือที่อีกคน approve, CI เขียว และรวมกับ `main` ได้สะอาด |

## 4. ปัญหาที่พบจากการใช้ AI และบทเรียน

| ปัญหา | เกิดอะไรขึ้น | แก้อย่างไร | บทเรียน |
|---|---|---|---|
| **บั๊กใน ConfirmDialog** | AI ใส่ padding ที่ตัว `<dialog>` และตรวจการคลิกพื้นหลังด้วย `event.target === event.currentTarget` ทำให้คลิกที่ขอบด้านในกล่องแล้ว dialog ปิดเอง | Pattarakorn พบตอนรีวิว โค้ดถูกแก้โดยย้าย padding ไปไว้ใน wrapper, เพิ่ม test และแก้กรณีลากเมาส์ที่ตามมา | lint, tsc, build และ test ผ่านหมดแต่บั๊กยังอยู่ เพราะโปรเจ็คยังไม่ได้ทดสอบการคลิกจริง การรีวิวโดยคนและการลองใช้จริงในเบราว์เซอร์จำเป็นเสมอ |
| **ติดตั้ง Vitest ไม่ผ่าน** | `npm install` ล้มด้วย ERESOLVE เพราะ Vitest 5 ต้องการ `@types/node` 22 ขึ้นไป แต่โปรเจ็คใช้ `^20` | อัปเกรด `@types/node` เป็น `^22`, ตรวจว่า build และ test ผ่าน, บันทึกไว้ใน `docs/NOTES.md` เพื่อให้เจ้าของไฟล์รู้ | เปลี่ยน dependency ที่คนอื่นเลือกไว้ต้องบอกเจ้าของและจดเหตุผล |
| **ข้อกำหนดขัดกัน** | ข้อความ Error เมื่อ Machine ID ซ้ำ ในแผนงานเป็นภาษาอังกฤษ แต่ requirement และกฎของโปรเจ็คให้เป็นภาษาไทย | AI ชี้ความขัดแย้งใน test checklist และ Pattarakorn ตัดสินใจใช้ "Machine ID นี้มีอยู่แล้ว" | AI ไม่ควรเลือกเองเมื่อเอกสารขัดกัน ให้ถามเจ้าของงาน |
| **ตีความคำสั่งผิด** | AI เข้าใจผิดในบางคำสั่ง เช่น ข้ามขั้นตอนย่อยของคู่มือ และเข้าใจว่าผู้ใช้จะ push เอง | ผู้ใช้แก้ให้ตรง และ AI แก้ตามทันที | สั่งงานให้ชัด และให้ AI สรุปสิ่งที่จะทำก่อนทำเมื่อเป็นงานที่ส่งผลกับคนอื่น |
| **ข้อจำกัดของเครื่องมือ** | ตอนแรก AI โพสต์คอมเมนต์ใน Pull Request เองไม่ได้ เพราะเครื่องไม่มี `gh` CLI | ตอนแรก AI เขียนข้อความให้ผู้ใช้วางเอง ต่อมาผู้ใช้สั่งให้ติดตั้ง `gh` และล็อกอินเองผ่านเบราว์เซอร์ (AI ไม่เห็นรหัสผ่านหรือ token) จากนั้น AI โพสต์คอมเมนต์ ขอ Reviewer เปิด PR และ merge ได้ตามสิทธิ์ที่ผู้ใช้ให้ แต่ยังอัปโหลดภาพเข้า PR ไม่ได้ ผู้ใช้ลากไฟล์เอง | ไม่ทำให้การสื่อสารในทีมขึ้นกับเครื่องมือ และสิทธิ์ที่ให้ AI ต้องแยกเป็นรายการ (คอมเมนต์ได้เลย, push กับเปิด PR กับ merge ต้องถามทุกครั้ง) |
| **test ที่ผ่านเสมอโดยไม่ได้ตรวจอะไร (#10)** | regex ใน test ของ `SubmitButton` หายตัว backslash จึงอ่านเป็น "ตัว s ตามด้วย disabled" แทน "ช่องว่างตามด้วย disabled" เพราะ AI แก้ไฟล์ผ่านสคริปต์ที่แทรกสตริงผิด test จึงผ่านแม้ปุ่ม disabled จริง และ AI ไม่ได้ลองทำให้ล้ม | Pattarakorn พบตอนรีวิว AI แก้ regex แล้วลองบังคับให้ปุ่ม disabled เสมอ test ล้มจริง | test ที่ไม่เคยล้มไม่ใช่หลักฐานว่าถูก ต้องทำให้โค้ดเสียก่อนทุกครั้ง (ใช้กับ test ใหม่ของงานตกแต่งและงาน Bonus หลังจากนั้น ไม่ได้ย้อนไปทำกับ test เก่าทุกตัว) |
| **เส้นทางที่ตรวจไม่ถึง: เปิดหลายแท็บ (#45)** | ปุ่ม Dark mode ที่ AI เขียนใส่ class `dark` เฉพาะตอนกดปุ่มในแท็บนั้น เมื่อเปลี่ยนจากแท็บอื่น ปุ่มบอก Dark แต่หน้ายังสว่าง การตรวจ 21 ข้อของ AI ทดสอบแท็บเดียวทั้งหมด | Pattarakorn พบกับ login จริง AI ทำซ้ำบั๊กในเบราว์เซอร์ก่อนแก้ ย้ายตรรกะไปไว้ที่ store ที่ตอบ event `storage` และเขียน test กับการตรวจสองแท็บ ครอบทั้งสองทิศทาง | ผู้ใช้ใช้งานต่างจากสถานการณ์ที่ผู้เขียนนึกถึง การรีวิวด้วย login จริงเจอสิ่งที่การตรวจอัตโนมัติของ AI ไม่เจอ |
| **ตรวจที่ผ่านโดยบังเอิญ** | ตอนทำซ้ำบั๊กหลายแท็บ การตรวจชุดแรกของ AI ผ่าน 5 จาก 6 ข้อทั้งที่ยังมีบั๊ก และบางข้อที่ผ่านก็เพราะแท็บที่สองเริ่มที่สีนั้นอยู่แล้ว ไม่ใช่เพราะโค้ดถูก | เขียนใหม่ให้แท็บที่สองต้องเปลี่ยนสีจริงในทุกขั้น และให้ล้มก่อนแก้ | การตรวจที่ผ่านก่อนแก้ ไม่ได้พิสูจน์ว่าแก้ได้ ต้องเห็นมันล้มก่อน |
| **ข้อกังวลที่วัดแล้วไม่เป็นจริง** | AI กังวลว่า `useEffect` ที่เพื่อนเสนอจะถอด class `dark` ตอน hydrate แล้วเกิดหน้าขาวแวบ | วัดลำดับการเปลี่ยน class บน `<html>` ตั้งแต่เริ่มโหลด ทั้งสองวิธีได้ `["dark"]` เหมือนกัน AI บอกเพื่อนตรงๆ ว่าข้อเสนอของเพื่อนใช้ได้ พร้อมข้อจำกัดของการวัด (มองไม่เห็นการถอดแล้วใส่คืนใน task เดียวกัน) เพื่อนเลือกใช้วิธีของ AI ด้วยเหตุผลอื่น | วัดข้อกังวลก่อนเถียง และอย่าอ้างว่าวิธีของอีกฝ่ายเสี่ยงถ้ายังไม่มีหลักฐาน |
| **commit ก่อนที่การตรวจจะผ่าน** | AI ต่อคำสั่งตรวจกับ commit ด้วย `;` ไม่ใช่ `&&` ข้อผิดพลาดของ `tsc` (type ของ mock ใน test) ไม่หยุด commit และ AI เห็นหลัง commit | ยังไม่ได้ push จึงยกเลิก commit (`reset --soft`) แก้ แล้ว commit ใหม่หลังตรวจผ่านจริง AI บอกเรื่องนี้ใน PR ด้วย | กฎ "ตรวจก่อน commit" ใน AGENTS.md พังได้ถ้าคำสั่งไม่ผูกกัน ต้องอ่านผลก่อนสั่ง commit |
| **แก้ไฟล์ผ่านสคริปต์แล้วเนื้อหาเสีย** | สคริปต์แก้ไฟล์ที่ฝังสตริงหลายชั้นทำให้ตัวอักษรที่ตั้งใจให้เป็นข้อความกลายเป็นอักขระขึ้นบรรทัดจริงในไฟล์ test จนแปลงไม่ผ่าน และคำสั่ง `sed` ที่ไม่ได้เปลี่ยนไฟล์ (นับได้ 0) ทำให้การทำให้โค้ดเสียแบบหนึ่งดูเหมือนไม่ถูกจับ | เขียนไฟล์ใหม่ทั้งไฟล์ด้วยเครื่องมือแก้ไฟล์ และเช็กทุกครั้งว่าการแก้ติดจริง ก่อนสรุปว่า test จับได้ | "ไม่ล้ม" อาจแปลว่าโค้ดยังไม่ได้เสีย ต้องเช็กว่าการเปลี่ยนเกิดขึ้นจริง |
| **ตรวจสิ่งที่ผู้ใช้ปลายทางเห็นไม่ใช่ค่าระหว่างทาง** | `response.text()` ตัด BOM ออกตอนแปลงข้อความ test ที่ตรวจสตริงจึงล้มทั้งที่ไฟล์ถูกต้อง | แก้ test ให้ตรวจไบต์จริง (`EF BB BF`) ซึ่งตรงกับที่ Excel เห็น และจดไว้ใน `docs/NOTES.md` | ตรวจที่ระดับเดียวกับที่ผู้ใช้เห็น และบันทึกกับดักแบบนี้ไว้ให้คนถัดไป |
| **ภาพจริงเห็นสิ่งที่ test มองไม่เห็น** | test ที่ใช้ `renderToStaticMarkup` ตรวจ HTML ได้ แต่ไม่เห็นเลย์เอาต์ ตารางรายการผ่าน lint, tsc และ test แต่บนมือถือ 360 px สถานะและรหัสเครื่องหลุดจอหรือถูกตัดกลางคำ Navbar ตกบรรทัดที่ 768 px และตาราง Alarm ที่ 768 px ตัดป้าย "In Progress" | แก้เป็นการ์ดบนจอเล็ก เลือกจุดเปลี่ยนเป็นตารางจากคอลัมน์ที่กว้างที่สุด (1024 px สำหรับ Alarm และ Maintenance) และจดไว้ใน NOTES | การดูภาพจริงที่หลายขนาดจอเป็นส่วนหนึ่งของการตรวจหน้าจอ และจุดเปลี่ยนต้องวัดใหม่ทุกหน้า ไม่ลอกจากหน้าอื่น |
| **คำสั่งที่ทำตามตัวอักษร** | ผู้ใช้สั่ง "เขียนคอมเมนต์และ merge" PR #12 AI ทำตามนั้นและไม่ได้ approve (บอกตรงๆ ในคำตอบ) ผู้ใช้ตั้งใจให้รวม approve ด้วย | ผู้ใช้ถามว่าทำไมไม่ approve AI อธิบายผลต่อประวัติของ PR แล้ว approve ย้อนหลังตามที่สั่ง | ชุดงานที่ทีมถือว่าเป็นก้อนเดียวกัน (รีวิว, approve, merge) ควรถามขอบเขตก่อน หรือระบุให้ชัดว่าส่วนไหนจะไม่ทำ |
| **สิ่งที่ AI ตรวจเองไม่ได้** | AI ไม่มี Excel, ไม่ได้ลอง Safari หรือมือถือจริง, ไม่ได้รันกับ Supabase จริง (ใช้ Postgres จำลอง) และอัปโหลดภาพเข้า PR ไม่ได้ | ทุก PR ระบุหัวข้อ "ที่ยังไม่ได้ตรวจ" และขอให้เพื่อนลอง ผลคือ Pattarakorn ยืนยันเรื่อง Excel (ภาษาไทย, `=1+1`) และ login จริง และพบบั๊กหลายแท็บที่ AI ไม่เห็น | บอกขอบเขตของการตรวจให้ชัดทุกครั้ง และให้คนตรวจส่วนที่ AI เข้าไม่ถึง |

ข้อจำกัดที่ยังคงอยู่
- ใน CI ยังไม่มีการทดสอบการโต้ตอบ (การคลิก, การกด Esc) เพราะยังไม่ได้เพิ่ม jsdom และ Testing Library การโต้ตอบของ Dark mode ถูกตรวจในเบราว์เซอร์จริงด้วยโปรแกรมชั่วคราว ครั้งเดียว ไม่ได้อยู่ใน CI
- ยังไม่มี End-to-End test อัตโนมัติ การทดสอบกับ login จริงและข้อมูลจริงทำด้วยมือโดยคน
- การเปิดไฟล์ CSV ใน Excel, การลองบน Safari และมือถือจริง, และการวัดความเร็วที่ข้อมูลเกิน 5,000 แถว ยังไม่ได้ทำโดย AI
- ผลทดสอบสิทธิ์และ trigger ที่ AI รันเอง มาจาก Postgres จำลอง ไม่ใช่ Supabase จริง

## 5. ส่วนระบบ (Pattarakorn)

ใช้ Claude Code ใน VS Code เหมือนกัน หัวข้อนี้ครอบคลุมงานตั้งแต่วางแผนจนถึงเฟส 8 (Deploy), ส่วนระบบของ Bonus 9.4 และการแก้ issue ที่เพื่อนพบตอนรีวิว

สิ่งที่ **ไม่ได้** ให้ AI ทำ: สร้างบัญชีและ key, ใส่ค่าใน `.env.local` และ Vercel, รัน SQL บน Database จริง, ตั้ง Role ของผู้ใช้
AI ไม่เคยเห็นค่า secret key เพราะไม่ได้ส่ง key ในแชท
